## Problem Statement

Broker 用户希望请求更容易成功，并更快看到第一段有效文本。现有管理台的“技术成功率”按上游尝试计算，将竞速落败取消计为失败，无法直接反映用户请求的最终结果；展示的 TTFT 也不等于客户端实际等待时间。现有流式接口在完整生成和校验后才发送缓存文本。

现有路由虽具备价格分组、历史评分、并发上限、备用请求、熔断及恢复，但没有充分利用请求形态、实时进度、延迟分布、站点负载和通道互补性。请求契约失败与传输失败共同影响 Provider/model 健康；取消虽不影响健康状态，却仍影响历史评分。整个 prompt 哈希相同才得到高权重，难以迁移到内容不同但形态相似的请求。

目标是在保持模型档位和输出契约的前提下，提高请求最终成功率，降低客户端首字及完整有效结果的 P50/P95，同时限制重复调用和故障期间的负载放大。

## Solution

建立以请求终态为基准的可观测性，将普通文本的真实流式交付与严格结构化结果的完整校验分开。路由根据当前请求的形态、最近可靠性、延迟分布、负载及剩余 deadline，选择主通道和具有补救价值的独立备用通道。

按故障归因维护站点、Key 和模型能力状态；全熔断时通过共享恢复探测协调等待请求；用有界并发、重试和探索预算避免过载。管理台展示用户可理解的成功率、首字等待、断流及兜底原因，支持分阶段灰度和回退。

## User Stories

1. 作为调用方，我希望看到按请求计算的最终成功率，以便判断 Broker 是否可靠。
2. 作为运维人员，我希望分开查看尝试成功率、竞速取消率和请求成功率，以便正确解释统计。
3. 作为调用方，我希望超时和未启动任何上游的请求也被记录，以便失败不会从指标中消失。
4. 作为运维人员，我希望看到统计覆盖率和未知终态数量，以便知道历史数据的局限。
5. 作为普通对话用户，我希望上游开始产生有效文本时即可收到文本，以便缩短等待。
6. 作为结构化结果使用者，我希望只收到满足完整契约的结果，以便下游安全解析。
7. 作为流式调用方，我希望出字后发生中断时收到明确终态，以便正确处理不完整答案。
8. 作为流式调用方，我希望不同 Provider 的答案不会被拼接，以便保持输出一致性。
9. 作为运维人员，我希望分别查看上游 TTFT、Broker 首字转发时间及客户端实测首字，以便定位延迟。
10. 作为运维人员，我希望查看成功结果完成时间及出字后中断率，以便兼顾速度和可靠性。
11. 作为调用方，我希望长上下文和短问答使用相应历史样本，以便获得适合本次请求的通道。
12. 作为结构化调用方，我希望路由利用相似 Schema 和任务形态的成功经验，以便新内容也能受益。
13. 作为调用方，我希望路由考虑 effort 和输出长度，以便合理安排等待与备用请求。
14. 作为调用方，我希望最近拥堵的 Provider 被及时降低优先级，以便减少尾部等待。
15. 作为调用方，我希望备用请求优先经过独立故障域，以便主通道故障时仍有补救机会。
16. 作为运维人员，我希望识别不同站点的相关失败，以便避免表面独立、实际共享故障的竞速组合。
17. 作为调用方，我希望备用通道根据主通道当前进度启动，以便及时补救慢请求。
18. 作为调用方，我希望心跳和推理事件不会无限延长无文本等待，以便首字延迟受控。
19. 作为调用方，我希望选择和重试遵守我的剩余 deadline，以便响应不会越过时间预算。
20. 作为运维人员，我希望 Key 和站点都有并发约束，以便多个 Key 不会同时压垮同一站点。
21. 作为调用方，我希望限流得到冷却处理，以便避免立即重复失败。
22. 作为调用方，我希望某种 Schema 不兼容不会封禁其他可用请求形态，以便能力失败不会扩大成全面不可用。
23. 作为运维人员，我希望认证、额度、模型能力和网络故障分别归因，以便采取正确恢复措施。
24. 作为调用方，我希望全熔断时可以在预算内等待共享恢复结果，以便避免连续快速失败。
25. 作为运维人员，我希望恢复请求数量有界且请求内容不被共享，以便恢复安全、可控。
26. 作为调用方，我希望尚未尝试的独立站点优先于低收益重复尝试，以便提高单位时间内的成功机会。
27. 作为运维人员，我希望重试、修复及探索流量都有预算，以便故障不会引发调用风暴。
28. 作为调用方，我希望少量流量持续验证恢复和新通道，以便路由不会永久锁定旧排名。
29. 作为运维人员，我希望取消不被当成可靠性失败，以便备用 Provider 不会因角色产生评分偏差。
30. 作为运维人员，我希望估计值附带样本量、时间窗和置信信息，以便小样本不会误导调度。
31. 作为调用方，我希望反复调用复用上游连接，以便减少连接建立开销。
32. 作为运维人员，我希望库存能够定期更新且保留有效旧快照，以便同步故障不会清空路由。
33. 作为调用方，我希望请求的 intellect 和输出契约得到履行，以便速度优化不会导致隐式降级。
34. 作为运维人员，我希望比较不同策略下的成功率、首字和额外尝试次数，以便验证收益。
35. 作为运维人员，我希望策略可逐步启用并快速回退，以便生产问题可控。

## Implementation Decisions

1. **统一请求终态。** 新增独立于 attempt 的 route 生命周期记录，包含接收时间、原始 intellect、交付模式、策略版本、deadline、赢家及唯一终态。覆盖完成、失败、deadline、调用方取消、零候选及进程异常产生的未知结果。以 route_id 幂等写入，不能用首条 attempt 的 tier 代替原始请求档位。
2. **可靠审计与统计口径。** 超时路径采用有界异步持久化及可恢复日志机制，不能通过阻塞数据库突破 deadline；应用启动时对未闭合记录进行对账。历史缺失保留 unknown，不能从 attempt 静默推断为成功或排除。请求成功率为已知 completed / 已知 completed、failed、timed_out 请求；调用方取消、进行中、未知终态及请求校验拒绝单列并展示总量和覆盖率。成功只代表满足 Broker 可验证契约，不代表业务事实正确或答案质量完美。
3. **时间定义。** 使用单调时钟计算耗时，分别记录排队/调度、attempt 启动、连接与响应头、首个非空文本、首个对外 delta、完整校验完成及总耗时。现有 ttft_ms 保留为 attempt 级兼容字段并明确标注；新增 route 级字段。服务端首次写出只能命名为转发首字，真实客户端收字由测试客户端或可选客户端遥测测量，不混为一谈。
4. **普通文本真实流式。** 在现有流式 API 引入明确的交付模式：auto 根据结构化契约选择交付方式；text 用于普通文本；validated 用于完整校验后交付。显式 text 与严格结构化契约冲突时在调用上游前拒绝。保留 delta/final 事件；在完整模型要求可验证且首次非空文本可交付时原子确定赢家，随后只转发该赢家的内容，并取消其他尝试。若协议无法在完整结果前验证模型要求，则延后交付并在诊断中标明。
5. **流式失败契约。** 输出首个 delta 前可切换 Provider；之后不得拼接、重放另一 Provider 的答案。已建立 SSE 后以单个 final 事件报告 completed、failed 或 timed_out，并带 route_id、稳定错误分类及 partial_output 标识；不能试图把已发送的 HTTP 200 改成 503/504。成功 final 保持兼容字段，非流式错误继续使用现有 HTTP 契约。客户端断开应取消上游并释放资源。
6. **结构化结果保持完整校验。** Schema、模型档位及现有研究计划验证规则维持有效，不能为了首字指标放松校验。有效结果到达时间是这类请求的主要速度指标；进度事件不能当成首字或成功。普通文本与结构化交付分别统计。
7. **请求画像。** 从已有安全诊断中提取输入长度档位、估算 token、Schema 特征/指纹、任务类别、effort、输出预算及交付模式。不依赖完整 prompt 相同才共享经验。画像维度有界且版本化，样本稀疏时向模型、Key 和站点统计回退。原始输入、密钥和输出正文不进入新增路由遥测。
8. **在线评分。** 路由优先满足能力、启用策略及 deadline，再使用按形态估计的有效完成概率、首字/完成延迟分布和当前负载排序；价格作为受预算约束的次级因素，可靠性目标下不再强制耗尽低价组。先实现可解释的分桶统计及平滑估计，不要求训练复杂模型。短窗反映当前拥堵，长窗提供先验；窗口、最低样本量及权重可配置。
9. **避免选择偏差。** 竞速落败取消为未知结果，不扣可靠性分；记录取消时已等待时间、是否出字和安全进度，延迟估计承认被截断观测。区分首选、备用、探索及恢复角色，记录选择概率和可用候选摘要。小样本附置信信息，不能将成功样本的均值当全体请求耗时。保留有预算的小比例探索，仅进入已满足能力和健康条件的通道。
10. **互补备用选择。** 为站点提供稳定 site_id/故障域配置，默认从规范化上游地址归组；Key 独立统计但共享站点容量。优先跨故障域，并从同 route 的重叠尝试估计相关失败、共同变慢及补救价值。取消结果和没有共同观测的配对不能当作独立成功证据。样本不足时回退到已知站点边界。
11. **动态备用调度。** 上游适配层向路由层传递响应头、推理/心跳、首个文本及输出进度。根据请求形态、已经等待的时间、主通道进度、剩余预算和系统负载决定何时启动备用。分别约束无响应、无文本、流空闲及总耗时；心跳不能解除无文本期限。保留现有固定延迟作为回退策略，启用动态策略时使用有界延迟和额外尝试预算。
12. **容量与公平性。** 同时实施单 Key、站点及全局并发限制，业务优先于探针/探索。允许有界、受 deadline 限制的等待队列；候选仅因瞬时满载而不可用时不能一律丢弃。释放资源、取消和超时均须唤醒等待者。优先改善尾延迟，不能靠无限增加并发获得表面收益。
13. **归因健康状态。** 分开维护站点传输状态、Key 认证/额度状态和 Provider/model/request-shape 能力状态。429 尊重合法的 Retry-After 并限制冷却上界；瞬时 5xx/连接失败按归因冷却；400 及 Schema 不兼容先归入请求/能力故障。403、额度及未知错误结合稳定错误代码分类，不能仅凭 HTTP 状态武断判定认证故障。输出截断根据调用预算与通道能力处理，不全局封禁。
14. **能力探针。** 普通文本和结构化探针分开存储契约、结果及有效期，采用足够完成目标的输出预算。微型探针成功不能证明复杂结构化任务可靠。探针与业务调用统计隔离；探针失败不能覆盖更新的业务成功证据。保留原有模型不匹配保护。
15. **共享恢复。** 同一故障域/能力的恢复采用 single-flight，只共享健康判断和恢复通知，不共享业务 prompt、输出或请求终态。其他请求在自己的 deadline 内等待并在成功后重新选择。恢复有全局/站点预算和冷却；失败后唤醒等待者并返回明确原因。最近成功的 stale-good 通道只能作为受限恢复候选，不能绕过用户禁用、认证无效、模型不匹配或已知不支持的契约。
16. **按收益安排重试。** 优先未尝试的独立站点；只有具备近期成功或可修复证据的重试才可提高优先级。相同请求、Provider/model、失败类别及修复次数均有上限；429/5xx 不做无退避的同站点连续重试。输出截断不能在相同条件下盲重试，也不能静默提高用户硬性输出预算。尝试总预算、修复预算与并发预算共同受 deadline 约束。
17. **连接与调度开销。** 上游连接池随应用生命周期复用，限制连接数量并保证每次请求凭据正确隔离；停止时关闭连接。采用可更新的有界统计缓存，避免每次逐通道扫描历史；数据库仍为可审计事实来源。增加连接和调度耗时后再量化收益。
18. **库存新鲜度。** 为 CPA 同步增加带抖动的周期调度和事件触发的受限刷新。刷新应事务化，保留用户策略及有效旧快照；临时发现失败不得自动清空所有可用通道，也不得自动清除仍有效的模型不匹配封禁。展示最后成功同步和过期状态。
19. **管理台。** 展示请求成功率及覆盖率、attempt 成功率、竞速取消、零候选、首字 P50/P95、有效完成 P50/P95、出字后中断、每请求尝试数和额外流量。支持按原始 intellect、模型、Key、站点、形态、交付模式和策略版本筛选；每个比例能查看分子/分母。未知遥测和未知成本不能填零。
20. **迁移与灰度。** 新数据结构采用增量迁移，保留现有记录及公开字段。策略以版本和开关分阶段启用：指标与审计、真实流式、健康恢复、画像与跨站点选择、动态备用、性能优化。新增模式及异常 SSE final 需要契约文档和调用方兼容测试；算法开关可快速回退。

## Testing Decisions

- 主要测试入口使用现有公开生成/流式 API 与管理 API，配合已有 aiohttp TestServer/TestClient、临时 SQLite、可控上游和时钟。沿用现有公开 API、路由韧性、生产形态验证及管理台端到端测试先例；不新建平行测试框架。
- 对外行为优先：断言实际首个 delta 是否在上游完成前到达、输出是否有效、最终状态是否唯一、备用启动时间是否有界、实际请求发向哪些故障域、deadline 是否履行。不要断言内部评分常量、队列名称或私有数据结构。
- 普通流式上游先发文本再受控等待：客户端必须先收到 delta；结构化请求同场景必须等完整校验。竞争赢家同时到达、出字后断流、缺失模型元数据、客户端断开均不得拼接答案或留下活动请求。
- 通过真实客户端读取 SSE 验证成功与失败 final 契约；HTTP 头发送前失败保留现有 HTTP 行为。普通文本、结构化及非流式分别覆盖。
- 一个请求一次成功加一次竞速取消，应计为一个成功 route，取消不影响可靠性评分。零候选、全部失败、deadline、DB 暂时争用、重复终态写入及重启对账不得漏算、重复计算或制造虚假成功。
- 上游模拟 400/403/429/5xx、认证和额度错误、Schema 失败、截断及模型不匹配，验证正确隔离范围及冷却。某形态失败后其他受支持形态仍可路由；更新的业务证据不能被旧探针覆盖。
- 并发请求遇到全熔断时，对同一恢复目标只发一次探测；等待请求各守 deadline、恢复成功后独立调用，不能泄漏或复用另一个请求的内容。
- 可控主通道慢、仅心跳、正常输出、断流及多站点关联故障场景，验证备用触发、互补选择及负载预算；单 Key、站点和全局并发均不得越限。
- 通过时间、样本量和形态变化观察对外选路分布：新近故障能改变选择，小样本有先验约束，取消不永久惩罚备用通道；使用可控随机源减少测试波动。
- 管理台端到端验证指标分子/分母、未知值、筛选和策略版本；迁移及库存刷新失败验证已有策略、历史和有效快照保持可读可用。
- 性能验收先建立完整终态基线，再进行有界生产形态测试及按形态分层的灰度比较。记录请求成功率、客户端首字 P50/P95、完整有效结果 P50/P95、出字后中断、尝试放大及连接/调度开销。灰度样本量、观察窗、并发和成本上限在实验开始前固定；不足时报告证据不足，不宣称提升。
- 历史回放用于检查选路及预算规则，不能证明未实际执行的 Provider 会成功或更快。生产新旧策略比较必须控制任务形态与时间分布，并给出不确定性；发布条件是契约测试全部通过，且预先定义的成功率非劣和延迟改善门槛得到支持。具体统计门槛在可信基线完成后确定，不能事后为通过而调整。

## Out of Scope

- 本规格发布不代表本轮已实现代码、改变生产配置或部署。
- 不购买或新增 Provider、不自动启用用户禁用的 Key、不调整账户凭据或充值。
- 不静默降低 intellect、不放松结构化校验、不用心跳或进度事件伪装首字。
- 不将任何上游声明的模型名称当作底层真实模型身份的独立证明。
- 不对业务答案的事实正确性承诺质量提升，不新增跨用户语义缓存或自动降低 effort。
- 不硬编码本次 Provider 排名、并发数、尝试次数、750ms 替代阈值或成功率目标；这些均由基线及受控实验决定。
- 不引入复杂强化学习平台。更复杂的缓存亲和、模型训练及额外产品策略档位留待实际遥测证明收益后另行规格化。

## Further Notes

- 来源为 2026-09-08 的讨论、仓库检查与小电脑只读统计；运行和数据目标为 yosef-server。
- 用户观察到的 43.2% 为当时页面值。检查时页面 24h 尝试成功率约 52.9%，存在约 2360 次取消。不同查询时刻有新请求及窗口滑动，数字不能混用为精确固定快照。
- 先前按已有 route_id 重建的约 95% 仅是审计覆盖范围内的估计；deadline 路径可能缺失记录，原始 intellect 也不能从 attempt 准确恢复。因此不得作为完整端到端基线，或以 97%–98% 为已证明收益。
- 7d 观测中存在 182 条 no_eligible_providers 终态；跨站点前两次尝试与同站点的成功率差异属于观察性关联，不能排除形态、时间、版本和选择偏差。需要上述实验验证。
- 当前 route_unavailable 历史诊断缺少形态时，不能据此认定普通文本本身成功率低。恢复阻塞的具体原因仍需终态、候选排除原因和健康时间线共同验证。
- Expert 通道表现与 Smart 差异显著，应分别验证；优质独立上游不足时算法本身不能保证目标成功率。
